# 真实短信认证与正常新用户准入设计

日期：2026-10-04

状态：负责人已批准本轮设计修订、固定依赖和有界真实发送；手机就绪确认仍是实发前置条件

## 1. 目标与范围

在不预置被测用户、不清理历史账号、不改变身份主键策略的前提下，使一个未登记的中国大陆手机号能够完成：

1. 获取登录/注册验证码并首次短信登录；
2. 自动建立唯一的 `User` 与 ACTIVE 手机号关系；
3. 获取第二次短信验证码并设置初始密码，退出后使用同一手机号和密码重新登录；
4. 真正走一次“忘记密码”：获取第三次短信验证码，重置密码，确认重置前后 `user_id` 不变、新密码可用、旧密码与规定范围内的旧会话失效；
5. 提交房屋绑定申请，由已有管理流程审核后获得合法住户访问权限。

本设计只补齐真实短信 Provider、配置、错误处理、客户端提示和对应测试。既有认证、会话、密码、房屋绑定与审核模型继续复用。0015、WO20、AI 模型、迁移和发布流程不在本次范围内。

## 2. 现状与约束

- `CredentialAuthService` 已实现 `login`、`reset`、`change_phone` 三种验证码用途，并将验证码哈希保存到数据库。
- 短信登录对未登记手机号创建账号；登录/注册是同一入口，不泄露手机号是否已注册。
- 初始密码设置与忘记密码均复用 `reset` 验证码、重置票据与确认接口。
- 当前只有 `DevelopmentSmsProvider`；选择非 development 模式会因生产 Provider 未实现而失败。
- 验证码有效期、尝试上限和发送/登录频控继续由现有配置与 Redis 执行。
- AI 无关，本功能及验收不得发起任何模型调用。
- 无凭据的单元和集成测试必须继续通过；真实短信只能在负责人批准的号码、次数与预算内发送。
- 本轮最多四次真实发送尝试，费用上限 0.30 元。失败、超时与未知结果都计入尝试次数；未知结果暂停后续真实发送。
- 手机号换绑只做离线回归，不在本轮消耗真实短信。

## 3. 方案选择

采用阿里云号码认证服务 PNVS 的服务端 `SendSmsVerifyCode` API，并继续由本系统生成和校验验证码。

选择理由：

- 保留现有验证码哈希、用途绑定、一次性消费、尝试上限和事务边界；
- 不引入数据库迁移；
- 登录/注册与重置密码可以直接映射到阿里云系统赠送模板；
- 供应商只负责发送，认证结论仍由业务后端控制；
- Development Provider 保持离线，不发生静默生产降级。

不采用阿里云生成并通过 `CheckSmsVerifyCode` 校验的路线，因为它会重复现有验证码生命周期并扩大接口、状态和测试改造范围。

## 4. 私密配置契约

本机交付环境从 Git 忽略的 `deploy/.env.delivery` 读取以下值：

| 变量 | 用途 |
| --- | --- |
| `SMS_ALIYUN_ACCESS_KEY_ID` | 仅后端使用的 RAM AccessKey ID |
| `SMS_ALIYUN_ACCESS_KEY_SECRET` | 与上述 ID 配套的 Secret |
| `SMS_ALIYUN_SIGN_NAME` | 控制台当前可用的系统赠送签名 |
| `SMS_ALIYUN_TEMPLATE_CODE` | 登录/注册模板；官方系统模板当前示例为 `100001` |
| `SMS_ALIYUN_PASSWORD_RESET_TEMPLATE_CODE` | 初始密码设置与找回密码共用的重置密码模板；当前示例为 `100003` |
| `SMS_ALIYUN_PHONE_CHANGE_TEMPLATE_CODE` | 既有手机号换绑流程使用的修改绑定手机号模板；当前示例为 `100002` |
| `SMS_LIVE_ALLOWED_PHONE_E164` | 本轮唯一允许的负责人自有大陆手机号，只保存在本机忽略文件中 |

模板编号必须以当前阿里云控制台的系统赠送模板为准，且与当前可用的系统赠送签名配套。2026-08-31 已停止支持的历史赠送签名不得继续使用。

`${code}` 与 `${min}` 是运行时模板参数，不增加人工填写变量。后端使用现有六位验证码填充 `code`，使用 OTP TTL 换算分钟填充 `min`。

当 `SMS_PROVIDER=production` 时，任何必需配置为空都必须在 Provider 构建阶段明确失败。8093 的 `APP_ENV=staging` 保持不变，并强制要求本轮手机号与预算闸门。不得回退到 Development Provider，也不得在日志、异常、健康接口、报告或测试快照中输出秘密值。

## 5. Provider 边界

新增 `AliyunSmsProvider`，并保持业务 Service 不依赖阿里云 SDK 类型。

Provider 输入：

- 标准化后的 `+86` 手机号；
- `purpose`：`login`、`reset` 或 `change_phone`；
- 现有后端生成的六位验证码；
- 当前请求的 `request_id`，作为供应商 `OutId` 便于脱敏追踪。

Provider 映射：

| 业务 purpose | 模板变量 |
| --- | --- |
| `login` | `SMS_ALIYUN_TEMPLATE_CODE` |
| `reset` | `SMS_ALIYUN_PASSWORD_RESET_TEMPLATE_CODE` |
| `change_phone` | `SMS_ALIYUN_PHONE_CHANGE_TEMPLATE_CODE` |

请求固定约束：

- `CountryCode=86`，传给供应商的号码去掉 `+86`；
- `TemplateParam` 为由 JSON 序列化器生成的 `code`、`min` 对象，禁止字符串拼接；
- `ValidTime` 与本地 OTP TTL 一致；
- `CodeLength=6`、`DuplicatePolicy=1`、`ReturnVerifyCode=false`；
- 显式设置 `AutoRetry=0`；SDK RuntimeOptions 与应用层自动发送重试均关闭；
- 网络连接和读取必须有有限超时；
- 返回结果只保留供应商请求标识、业务流水号和成功状态，不保留明文验证码。

使用负责人批准的官方 Python SDK `alibabacloud-dypnsapi20170525==2.0.0`。只补齐其实际必要传递依赖并冻结版本，不升级无关依赖。安装和离线验证可执行；调用真实发送仍受本轮闸门控制。

## 6. 本轮持久发送额度与验证码状态

### 6.1 持久额度

本轮 8093 真实发送由后端闸门拦截，且只允许 `SMS_LIVE_ALLOWED_PHONE_E164`：

- 预算键固定为本轮标识，不按请求、进程或子任务变化；保存在已启用 AOF 且 `appendfsync always` 的现有 Redis 数据卷中，不设置 TTL；
- 仅在实发授权和号码核对后，由受控初始化步骤一次性写入 `{allowed_phone_digest, max_attempts=4, max_cost_milli_cny=300, reserved_attempts=0, reserved_cost_milli_cny=0, state=ACTIVE}`；重复初始化不得清零已有计数；
- 每次 Provider 网络调用之前，用一段原子 Redis Lua 脚本核对同一号码、状态及剩余额度，并一次占用一个尝试和 75 毫元（0.075 元）保守预算，同时将状态置为 `IN_FLIGHT` 并记录本次不含手机号的请求标识；即使发送失败、超时或进程重启，占用也不得退回。同一时刻只允许一笔发送在途；
- Redis 不可用、键丢失、结构异常或额度不足时拒绝发送；不自动重建预算，也不回退本地计数；
- 供应商明确接受或明确拒绝时，只有本次请求标识匹配才能把 `IN_FLIGHT` 原子改回 `ACTIVE`；结果不确定时保留 `IN_FLIGHT` 或改为 `PAUSED`，后续发送一律拒绝。若结束写入失败也保持在途阻断；排查后只有新增明确授权才能恢复发送；
- 每次实发前重新核对官方价格与剩余费用上界；价格高于每次预留值或无法确定时停止实发。

这一闸门是本轮 staging 验收控制，不改变正式发布策略；未来 Production 上线必须另做配置与费用审查。

### 6.2 验证码安全状态

验证码采用“先不可核验，后精确激活”的最小变更，无需 Migration：

1. 原事务消费图形挑战、作废同手机号同用途旧验证码、新建 OTP 哈希，但让新行 `consumed_at` 非空；此时任何验证请求都找不到开放验证码。
2. 在预算占用后调用 Provider。明确成功时再以本次 `SmsChallenge.id` 加锁读取；只有它仍是同手机号同用途的最新行且尚未过期，才将 `consumed_at` 清空以激活。
3. 失败、超时、未确认发送或激活事务失败时，该行保持不可核验；无需依赖事后补偿才能保证安全。
4. 较晚返回的旧发送不能激活已被后来的发送取代的行。更新只能按本次 ID 精确执行，绝不按手机号误作废后来的验证码。
5. Development Provider 可沿用相同安全状态机，既有离线行为和测试应保持通过。

### 6.3 发送数据流与失败语义

1. 客户端获取并正确回答图形挑战。
2. Service 执行 Redis 发送频控，生成六位 OTP。
3. Service 在自有事务中作废同手机号、同 purpose 的旧 OTP，并保存不可核验的新 OTP 哈希。
4. 本轮闸门先完成原子额度核对与占用，Provider 再向阿里云提交发送请求。
5. 供应商明确接受后，Service 按本次 ID 且仅在仍是最新行时激活 OTP；随后 API 返回 `provider_mode=PRODUCTION` 与脱敏手机号。
6. 客户端开始倒计时并提示“验证码已提交发送，请留意短信”，不得宣称运营商已经送达。

失败处理：

- 配置缺失：Provider 构建失败，不启动真实短信模式；
- 参数或供应商明确拒绝：OTP 维持不可核验，返回 `AUTH.SMS_PROVIDER_DOWN`；
- 超时或网络结果不确定：OTP 维持不可核验，返回 `AUTH.SMS_PROVIDER_DOWN`，不自动重试，并使额度保持在途阻断；迟到短信即使送达也不能通过验证；
- 激活事务或任何事后补偿失败：OTP 的安全默认状态仍是不可核验；记录不含秘密的高严重度结构化日志并返回稳定错误；
- 预算占用失败：Provider 不被调用，本次 OTP 不可核验；
- 所有失败都禁止回退到 Development Provider。

## 7. 客户端行为

- 登录页的 `login` 目的同时代表已有用户登录和未登记手机号注册，不增加“已注册”探测接口。
- 初始密码与忘记密码都进入现有密码重置页，发送 `reset` 目的验证码。
- Development 模式继续明确标记为开发替身；Production 模式改为“验证码已提交发送，请留意短信”。
- 只有短信发送 API 成功返回后才开始倒计时；失败时保留可重试界面并展示稳定业务错误。
- 页面、控制台、截图和采集证据不得显示验证码、AccessKey、完整手机号或环境文件内容。
- 绑定审核复用现有权限与审批接口；仅向该小区有 `resident_binding:review` 权限的管理员，在待审列表显示申请编号、申请人显示名与内部账号编号、小区/楼栋/单元/房号。详情缺失时页面禁止通过或拒绝；不展示完整手机号，管理员仍须核对申请人与房屋资料，不能因页面显示而自动批准。

## 8. 测试与验收

### 8.1 无凭据自动测试

- Settings 对所有短信秘密使用 `SecretStr`，序列化与日志不泄露原值；
- `SMS_PROVIDER=production` 且配置缺失时明确失败；
- 三种 purpose 选择正确模板；未知 purpose 拒绝；
- `+86` 号码转换、模板 JSON、TTL、覆盖策略、`AutoRetry=0`、SDK/应用无自动发送重试、超时和 `OutId` 正确；
- SDK 客户端完全使用 Fake/Mock，不访问网络；
- 供应商拒绝、异常和超时统一映射为 `AUTH.SMS_PROVIDER_DOWN`；
- Provider 未确认、失败、超时、激活事务失败或补偿失败后本次 OTP 不可使用；较晚返回的旧发送不会误激活或误作废后来的 OTP；
- 并发预算占用不会超过四次；失败/超时占用不可退回；Redis 重启后计数持续，键丢失与 Redis 不可用时拒绝发送；
- 离线证明首次建号、初始密码设置、真正忘记密码后同一账号、新密码生效、旧密码和旧会话失效；
- Development Provider 不受影响且生产失败不降级；
- 登录、初始密码/找回密码和换绑页面提示按 Provider 模式正确；
- 既有认证、密码变更、手机号换绑和房屋绑定测试继续通过。

### 8.2 获得真实发送授权后的验收

在 8093 隔离环境、保留现有 3327 数据库的前提下：

1. 使用未登记的负责人自有手机号完成登录/注册短信；
2. 证明数据库只建立一个用户和一个 ACTIVE 手机关系；
3. 使用第二条短信设置初始密码，退出并通过密码重新登录同一用户；
4. 从正常“忘记密码”页面发第三条短信并完成真正的找回密码；核对重置前后 `user_id` 一致、新密码生效、旧密码与规定范围旧会话失效；
5. 从真实小程序页面提交房屋绑定申请，管理员审核后验证住户访问；
6. 检查 API、页面状态、只读数据库证据与脱敏截图属于同一业务对象；
7. 记录实际发送尝试次数、预算占用及实际费用，不超过四次尝试和 0.30 元；手机号换绑只做离线回归。

配置与安全检查、正常页面入口以及负责人确认手机准备好后才开始实发。结果不确定时暂停后续真实发送，但继续无需发送的排查。按已有流程重建 8093 服务，保留 3327 数据库，不迁移、不清库、不预建被测用户、不调用模型；`APP_ENV` 保持原值，仅在满足条件后切换 `SMS_PROVIDER`。需要时仅恢复本人受限手机入口，结束后关闭，不扩大公网开放范围。正式发布、上传提审和 Production 验收仍需单独批准。
