# 旧栈端口维护补正

用户已授权连续完成物业；本方案只处理原具名旧栈，delivery与企业知识库不变。不升级Milvus，不删除原卷/容器，不重放工单，不调用模型或短信。

诊断证据：同一v2.5.10精确镜像的隔离合成组111401Z在集合Loaded时60.375秒后137非OOM，恢复查询失败且原stderr缺失，保留失败。另一独立新组111710Z先release到NotLoad后2.094秒Exit0，重启16主键及最近邻3一致；三组临时资源已独立核实清理。不能将合成对照直接视为旧32集合修复。

旧栈112626Z只读盘点：32集合、157实体，分区全部Loaded、单副本、默认资源组。正式维护再次校验；不支持部分加载/其他DB/自定义资源组时直接中止，不能扩大加载范围。

执行顺序：
1. 继承maintain_ports原精确网络/卷写者/配置/空间检查，已有镜像，不下载。
2. 暂停原4个API/入口消费者。新512MiB/1CPU只读临时client进入旧网络，无端口、无持久挂载。
3. 校验全部集合范围，flush，保存schema/index/partition/实体数及主键集合哈希到私有gitignored目录；不输出正文/向量/主键值。每集合查询上限1024，达到即拒绝。
4. 按已保存清单release；仍要求原数据服务Exit0且非OOM才备份7卷。不得放宽停止判定。
5. 断开旧5容器网络，保留原容器，创建同镜像同配置同卷的loopback替代。只改发布HostIp与维护标签；OOM null到false为Docker默认值归一化，true不允许。
6. 启动依赖并恢复全部原加载范围，核对元数据及主键哈希，随后才开放原消费者并核对8端口/HTTP/delivery容器集合。

回退：替换前失败，清理本轮client/candidate，按实际网络状态重连原容器，恢复依赖和集合加载后再开入口；恢复失败保持入口关闭。替换后失败关闭消费者，保留依赖当前状态及确切ID，不对Loaded Milvus做15秒强停，不恢复公网绑定，不自动覆盖数据库。维护总预算1800秒，活动1500秒，剩余300秒用于恢复。所有步骤落盘。

验证：原故障契约加partial release/加载恢复失败阻断入口、替换后部分restore与HTTP失败不强停数据服务、OOM危险值拒绝。25项已通过；仍需实际执行、备份与运行独立复核。元数据/主键一致不代表全部向量逐值校验。

技术依据：[Milvus v2.5.10 QueryNode Stop](https://github.com/milvus-io/milvus/blob/v2.5.10/internal/querynodev2/server.go#L403)包含等待段与pipeline清空逻辑；本地精确镜像配置也有1800秒graceful timeout。此为机制说明，不能单独作为旧栈阻塞根因证明。
