# W：物业内部负责工单履历

承接 T08 的最小人员证据展示，不实施暂缓的容量/反馈统计政策。现有员工页只展示技能/职责及任职，主管无法就类型和实际记录复核人员经验。

新增只读 `GET /admin/employees/{id}/work-history`，必须指定 tenant_id/property_id，当前身份同时具备目标小区 employee:read 和 work_order:dispatch。每次重新加载身份；员工必须属于该企业并有该小区任职历史。住户、自身员工身份和其他小区授权不够。接口校验 X-Property-Id，不拼接其他scope的权限。

返回最近20个该员工作为 Process.assignee 的处理轮次，游标按process.id倒序。明确标题“负责工单履历”，不冒充所有实际维修参与。每轮只返回工单ID、类别、当前工单状态、轮次/起止、员工回执是否自报解决、有效回执自报参与方式及提交者关联、最新一条同轮住户反馈及来源ID/时间。历史无处理声明显示未记录；协作/外部不能算负责人独立完成；最新反馈不是完整统计/成功率。无手机号、地址、住户身份、反馈原文、内部自由文本或原始日志payload。

不新增表/迁移/画像等级/排名，不更改派单排序/质量分母。原有技能和履历只供有权主管人工判断。处理类型是现工单分类，无历史分类快照时不声称分类从未变化。

Repository 按企业/小区/员工过滤，分页21取20，不一次扫描所有人历史。回执、反馈与声明各自重验轮次和scope；反馈取每轮最新一条，声明仅接受指定回执事件及匹配receipt/process的合法结构。页面显式点“查看负责工单履历”，只有双权限显示；切人/小区/身份/隐藏清空，旧成功/失败不回填，分页不重复请求。

修改范围：admin_employee路由、独立小型history service/repository/schema、staff页、API封装、API文档和合成/隔离专项。先负例，后实现；独立只读复审，必要隔离MySQL证明查询实际可用。默认20、最多20，单页最多固定数量查询，无外部模型或费用。
