# 01 — 产品需求文档（PRD）

**范围：** Production V1  
**客户端：** 单一微信小程序，登录后按角色渲染功能入口

### 2026-09-24 v2：联系电话与统一维修组（024，负责人批准）

覆盖普通维修细分工种硬匹配及未批准的默认多专业拆单建议；其他 V1 需求/历史证据保留。

- 报修必须填写并确认本次联系电话，默认本人当前有效号码，可改实际联系电话；前后端校验，工单保存独立快照。换登录号码不改历史，旧 NULL 显示“未采集”，不回填其他住户或账号号码。
- 电话仅本人、当前有效负责员工、有对应组织管理权限者可读；默认脱敏，显式查看/拨号重新授权并记不含号码的审计。列表、模型输入、普通日志、公开证据无完整号码。
- 普通水电、空调、墙面、一般设施及混合问题由真实 MAINTENANCE 职责/有效任职/服务小区决定的组承接，无细分技能标签也可；不默认拆单。保洁、安保、特殊限制、高风险不放宽。
- 系统选合法在岗、跨小区零占用的具体员工；活动 Assignment 含未接单预占/WAIT_CONFIRM。多个空闲者按持久派单历史公平轮转；事务内重新确认。容量仍为有限上限，人工授权干预另循现有规则，共同事件沿用共享责任容量保护。
- 全忙保留 PENDING_ASSIGNMENT 与等待原因；现有有限周期调度使用已完成分析自动补派，释放/恢复资格后最迟下一调度周期发现。拒单、超时、失资格未接单任务保留原 Assignment 历史后回待派。通知补发不重新派单。
- 一位负责人统筹全部普通问题，页面保留原文/补充，回执逐项交代全部问题，不得只完成一项便无依据结案。模型提取事实、问题、风险、分类与事件，服务端负责选人。
- 此变更不是旧模型失败追认 PASS；28例、原始输出、3/3保留。不追加推理、不切换真实业务模型，软件替身与真实模型/生产验收分开。

## 1. 身份与账户

### 1.1 登录方式

| 方式 | 说明 | 失败处理 |
| --- | --- | --- |
| 微信快捷登录 | code 换 session，绑定 `openid` / `unionid` | 微信接口超时/失败返回明确错误，可改走短信 |
| 手机号 + 短信验证码 | 发送频控、验证码一次性、过期作废 | 验证失败明确拒绝；保留单验证码尝试次数上限，不累计失败锁号 |
| 手机号 + 密码 | 密码哈希校验 | 校验失败明确拒绝并提示忘记密码；保留现有限流，不累计失败锁号 |

2026-09-23 负责人明确调整：**不锁定**。不新增按手机号/IP累计登录失败后锁定的机制，替代原“失败计数、锁定窗口”要求；保留验证码挑战、验证码有效期/一次性/尝试上限、发送频控和现有总请求限流。原需求 ID `V1-AUTH-LOCKOUT` 及历史证据保留，当前标为负责人批准的需求调整，不计作实现或测试 PASS。此决定不扩大账号恢复、合并或发布权限。

内部永久 `User.id`（BIGINT）才是真实身份，其他表通过同型 BIGINT `user_id` 外键关联。手机号、微信号、密码、身份证都不是业务主键。

### 1.2 一个自然人一个账户

- 同一手机号不得创建第二个 User。
- 同一微信 `unionid`（无 unionid 时用 `openid` + appid）不得创建第二个 User。
- 一个 User 可同时拥有多个角色，禁止为同一人复制账户。
- 微信登录遇到“已有手机号账户、微信未绑定”时走 **绑定或合并** 流程，不静默建新号。

### 1.3 账户维护

- 修改密码（需登录 + 旧密码或验证码）
- 忘记密码（短信验证码重置）
- 更换手机号（验证旧号 + 新号，审计）
- 微信重新绑定（解绑旧 openid，绑定新 openid，审计）
- 账号合并（保留目标 `user_id`，迁移身份绑定、角色、房屋关系、工单、评价）
- 所有安全操作写入审计日志

2026-09-25 负责人决定：普通已结束号码复用须经过 30 天隔离期、独立的新持有人证明和两名不同授权人的审核；时间到期或新短信本身都不能恢复旧账号或继承合并目标资料。合并永久保留来源账号、号码与合并历史，撤销来源账号会话、密码及恢复票据，不复制来源密码，不删除手机号唯一约束。无 ACTIVE 手机号的来源账号同样必须走可信证明；没有获批核验渠道时保持待核验，禁止伪造接管。目标无密码时由目标本人近期重新认证后显式设置新密码。该决定不等于迁移已获批准。

### 1.4 高风险身份恢复

用于：手机号不可用、微信丢失、疑似盗号、合并争议。

流程：

1. 提交实名信息（姓名、身份证号）。
2. 调用实名认证 Provider + 人脸活体核验 Provider。
3. **本系统不保存、不比对原始人脸特征或人脸 embedding。** 只保存第三方流水号、核验结果、时间、操作者。
4. Provider 失败或低置信度 → 进入物业人工审核，不自动通过。
5. Production Provider 与 Development Provider 必须解耦。无企业凭证时，Development Provider 返回可测试的固定结果，禁止调用真实公安/微信人脸接口。

## 2. 物业、房屋和住户

### 2.1 房产档案（上线前由物业建立）

结构固定：

`Tenant` → `Property` → `Building` → `Unit` → `House`

物业导入或录入小区、楼栋、单元、房号。House 只描述物理房屋，**不写死业主姓名**。

### 2.2 住户首次登记

住户登录后自行申请绑定：

- 姓名、手机、小区、楼栋、单元、房号
- 与房屋关系：`OWNER` / `TENANT` / `FAMILY` / `AUTHORIZED_OTHER`

申请结果：

- 自动核验（例如预登记手机号/房号匹配）或
- 物业人工审核

通过后形成正式 `ResidentHouseRelation`。失败须可查看原因并再次申请。

### 2.3 关系历史

- User 与 House 多对多。
- 入住、退租、关系变更都是新记录或关闭旧记录，**禁止覆盖历史行**。
- 查询“当前住户”过滤有效关系；查询历史走全量关系。

## 3. 物业人员管理

`Employee` 与 `User` 分离，通过 `user_id` 关联。没有 User 的人员不能登录小程序；没有 Employee 的 User 不能接工单。

员工档案包含：

- 所属企业、所属小区（可多小区，但派单按工单所属小区过滤）
- 部门、职责、技能
- 今日签到、在岗/离岗
- 当前工单负载、最大处理容量
- 工作历史、平均响应时间、服务评价

**签到和当天人员状态必须直接参与 AI/规则派单。** 未签到人员不得进入自动派单候选。

Employee 归属于 Tenant，通过 `EmployeeProperty` 关联一个或多个 Property。该关系保留 `status`、`valid_from`、`valid_to` 历史；`valid_to` 为空表示当前有效，变更服务范围不得覆盖旧记录。

签到时间 `check_in_at` / `check_out_at` 保存 UTC；“今日”使用 Property 业务时区下的 `business_date`，默认 `Asia/Shanghai`，禁止直接以 UTC date 判断。

## 4. 工单（住户）

住户可：

- 文字 / 图片 / 语音报修
- 补充问题
- 查看进度与处理过程
- 撤销（仅允许在未开始现场处理前的状态，见状态机）
- 确认解决
- 反馈仍未解决（重开，保留旧维修记录）
- 评价

语音在服务端经 ASR Provider 转文字后进入理解流水线。ASR 失败时保留音频，工单仍创建成功，进入人工分析队列。

---

## 5. 工单（工作人员）

工作人员可：

- 查看分配任务、接单
- 拒单并填写原因
- 开始处理、上传现场图片、填写反馈
- 完成处理并填写正式回执
- 无法解决时填写原因并向上级上报

工作人员 **无权**：

- 擅自把异常工单标为完成/关闭
- 要求业主自行联系第三方
- 直接在系统里“下单外部服务商”（V1 无此能力）

---

## 6. 主管 / 管理员对异常工单的决策

当处理失败或 `process_reason` 进入升级类原因后，由主管或物业管理员选择：

- 重新内部派单
- 等待配件
- 等待业主配合
- 由物业自行联系第三方专业服务（仅内部记录）
- 其他处理方案（必填说明）

---

## 7. 回执

每次完成处理（含未解决上报）必须形成回执，字段：

- 问题类型、派给谁、处理方式、处理过程
- 使用材料、是否产生费用及金额记录
- 处理前/后图片
- 是否解决、未解决原因、后续处理方式、完成时间

重新处理生成新回执，不覆盖旧回执。

费用在 V1 只做工单侧金额记录，不接入收费/支付。

---

## 8. AI 工单理解

输入：用户文字、图片、语音转文字、已知房屋和用户上下文。

输出必须是结构化对象（见 `docs/05-AI-DISPATCH-SPEC.md`）。  
AI 不拥有最终业务控制权。低置信度或模型失败 → `PENDING_ANALYSIS` / 人工队列。

---

## 9. 智能派单

禁止 LLM 从员工姓名列表里直接选人。

必须：问题类型/职责判断 → 规则引擎 → 当天人员状态 → 硬过滤 → 候选评分 → 自动派单。  
同时支持人工派单、改派、拒单、超时重派、管理员接管。

---

## 10. 集中事件 Incident

对短时间、同区域、同类型工单聚合（例如同一栋楼 10 分钟内大量停水）。

- 生成 Incident，关联多条居民工单
- 避免重复派出多名维修人员到同一根因事件
- 每个业主仍保留自己的工单与反馈
- AI 可生成运营摘要和公告草稿
- **禁止 AI 自动向业主发布公告**
- 有 `incident:manage` 且命中租户/小区范围的人员可处置或重开 Incident，原因必填并写审计。普通住户只通过本人工单反馈，不能直接改变 Incident 主状态。
- Incident 的处置或关闭不得批量改变成员工单状态、覆盖处理回执或删除历史；成员工单继续按各自状态机完成。

---

## 11. 公告

物业可创建、AI 生成草稿、编辑、审核、发布、查看历史。

定向范围：企业全部小区 / 某小区 / 某楼栋 / 某单元 / 特定人群（如业主、租户、员工）。

未审核通过的草稿对住户不可见。

---

## 12. AI 物业知识助手

RAG：制度、入住指南、装修规定、常见维修、已发布公告/服务规则。

- 向量库：Milvus；embedding：bge-m3；生成：Qwen-family LLM
- 必须返回引用来源
- 知识带 `tenant_id`、`property_id`、`visibility`，禁止跨物业/跨小区召回

## 13. SLA

按工单类型/优先级配置接单、响应、完成时限。  
状态：正常 / Warning / Overdue，并可 Escalation。  
禁止在代码里写死小时数。

接单、响应和升级分别使用已批准的合法配置。策略变更必须保留版本、适用范围与工单采用的历史依据，不能用新值改写已经开始的计时；未配置的时限不得由模型推测或补造。现有单行覆盖结构只能表达当前值，历史版本能力需要单独增量结构和迁移批准。

---

## 14. 通知

内部通知必做；微信订阅消息作为 Production NotificationProvider 预留。

事件：创建、派单、接单、状态变化、SLA 预警、异常升级、完成、公告。

必须：重试、失败日志、后续可接 DLQ（V1 先落库 + 有限重试，不自建独立消息平台）。
